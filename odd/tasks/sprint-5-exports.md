# Feature: sprint-5-exports

## Objective

From the dashboard, download the weekly report of the **selected view** as a printable PDF and as an Excel workbook with processed results, both generated by the backend locally, offline, never stored on the server.

## Problem / Why

The owner needs to print, share and archive the weekly results. Exports must match the dashboard exactly, so the backend regenerates them from the same file with the same rules (single source of truth).

## Scope

- Endpoints `POST /api/exports/pdf` and `POST /api/exports/xlsx`: multipart `file` (same upload controls as `/api/analysis`: memory, 5 MB, `.xlsx`, signature, zip guard) + field `view` (`branch-<code>` | `all`). Unknown/missing view → 400 with error envelope (Spanish message). Import errors identical to `/api/analysis`.
- Response: binary with `Content-Type` (`application/pdf` / `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`) and `Content-Disposition: attachment; filename="grido-informe-<view-slug>-<from>-al-<to>.<ext>"` (slug: `almirante`, `barranqueras`, `ambas-sucursales`; ASCII, lowercase, hyphenated; add RFC 5987 `filename*` if non-ASCII ever appears). Expose `Content-Disposition` header to the client if needed.
- PDF (pdfmake 0.3.x, bundled Roboto from the package's vfs, A4 portrait): cover/heading with "Informe semanal de sobreventas", view label, period, generation date; summary; podium (with vacant / covered-by-tie explanations); full ranking with eligibility reasons; observations with Dato / Interpretación / Recomendación; footer with page numbers and podium requirements. Colors from the approved guide, legible in grayscale.
- Excel (exceljs) for the selected view: sheets `Resumen` (view, period, tickets, activadas, aceptadas, effectiveness, cashiers, shifts), `Ranking` (position, cashier, branches, shifts, tickets, activadas, aceptadas, effectiveness, eligible, reasons; autofilter; frozen header), `Podio` (step, status, cashier, effectiveness, tickets, activadas, aceptadas), `Observaciones` (rule, title, cashier, fact, interpretation, recommendation). Numbers stored as numbers; effectiveness as fraction with `0.00%` format; `null` effectiveness → text "No calculable".
- Pure builders (`buildReportWorkbook(view, meta)`, `buildReportDocDefinition(view, meta)`) in `apps/api/src/export/*`; HTTP only adapts. No business recomputation in exports — they consume the analysis view.
- Web: "Descargar PDF · <vista>" and "Descargar Excel · <vista>" buttons for the selected view; states generating / done / error (Spanish); re-sends the `File` held in state with the current view id; downloads via Blob + object URL (revoked after use) using the server filename.
- Docs: API_CONTRACT, DECISIONS, README (how to export), UI_UX_GUIDELINES (export buttons/states) if needed.

Out of scope: exporting all views in one file (user decision 2026-11-02: selected view only), persistence, email/sharing integrations.

## Constraints

- No files written to disk on the server; no external resources (fonts from pdfmake package vfs).
- Same validation/limits as `/api/analysis` (reuse the upload middleware and import pipeline).
- Spanish copy in the report and UI; code/docs in English.
- Fictitious names in tests; never commit generated reports from the real file.
- Test-first. New dependency: `pdfmake` only (+ types if needed).

## Acceptance criteria

1. Real file: PDF and Excel for each view show the same numbers and podiums as the dashboard.
2. PDF opens and prints on A4; Excel opens with 4 sheets, autofilter, numbers as numbers.
3. Invalid file → same clear error as upload; invalid view → 400.
4. Nothing written to server disk; no external resources.
5. `pnpm typecheck|lint|format:check|test|build` pass.
